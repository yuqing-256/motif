# Motif References

This file indexes external references, official documentation, reusable Agent capabilities, and research resources relevant to Motif.

It is a resource index and usage guide, not a copy of external documentation.

Resources listed here are not automatically approved dependencies or required installations.

## How to Use This File

Select resources according to the current task and development phase.

Prioritize:

1. Official documentation matching the installed version.
2. Official standards and specifications.
3. Existing, trusted, maintained Skills and workflows.
4. Reference websites relevant to the specific design question.
5. Community resources when authoritative sources are insufficient.

Before adopting a resource, verify that it exists, is accessible, is maintained, and is appropriate for the current task.

### Resource Status

Use the following status descriptions:

- **Adopted** — confirmed as part of the current project direction.
- **Preferred** — recommended when the relevant task occurs.
- **Candidate** — worth evaluating, but not yet adopted.
- **Reference** — useful for research, not an implementation dependency.
- **Deferred** — intentionally postponed until a later phase.

A resource's presence in this file does not imply that it is installed or configured.

## Reference Research Method

Reference websites should be studied to understand design problems and solutions, not copied as visual templates.

### Research Procedure

1. Define the question being investigated.
2. Select websites that provide relevant evidence.
3. Inspect representative pages, not only homepages.
4. Examine content hierarchy, layout, typography, interactions, and responsive behavior where relevant.
5. Record observable details separately from interpretation.
6. Classify findings.

### Finding Classification

- **Adopt** — a method suitable for Motif with little or no conceptual change.
- **Adapt** — a useful method requiring changes for Motif's goals.
- **Avoid** — a method that conflicts with Motif's requirements or has demonstrated problems.
- **Investigate** — an observation requiring further research or testing.

Do not treat a site's visual quality as proof that every implementation or interaction decision is appropriate.

## Agent Skills

Skills are reusable task instructions and specialist workflows.

Prefer existing, trusted, maintained Skills before creating Motif-specific Skills.

The following are search directions, not confirmed installations or mandatory dependencies.

### Existing Skill Sources to Investigate

1. DeepSeek Harness's built-in and available Skill catalog.
2. Official or maintainer-provided Skills for relevant tools.
3. Reputable open-source Skill repositories with clear ownership and maintenance.
4. Existing Skills already available in the current development environment.

Evaluate a Skill by:

- Source and maintainer.
- Scope and relevance.
- Compatibility with the current Harness.
- Instruction quality and clarity.
- External dependencies and permissions.
- Maintenance and version history.
- Whether it conflicts with Motif's decisions.
- Results from a small practical test.

### Motif-Specific Skill Candidates

Create these only when repeated work demonstrates a need and existing Skills are insufficient.

- Editorial reading review.
- Hugin design review.
- Munin functional interface review.
- Appearance-mode consistency review.
- Documentary provenance review.
- Multilingual typography review.
- Cross-platform design adaptation.
- Component and pattern documentation review.

Hugin and Munin review methods should be complementary. They must not assume that each approach corresponds to a separate theme.

Do not create a separate Skill for every design principle. Stable project knowledge belongs in project documentation; Skills should describe reusable ways of performing work.

### Project-Local Skill Location

Prefer the DeepSeek Harness-supported project-local location:

`.dsh/skills/`

Verify the installed Harness version's discovery rules before creating or relying on this directory.

Do not maintain duplicate Skill directories unless cross-environment compatibility becomes an actual requirement.

### MCP Adoption Rules

Before connecting an MCP server:

- Verify its source and maintenance.
- Inspect its available tools.
- Review permissions and data access.
- Check whether the same capability already exists.
- Use the minimum required access.
- Keep personal credentials outside the repository.
- Confirm that its capabilities are supported by the current DeepSeek Harness version.

Do not introduce one MCP server for every reference standard or documentation domain.

## Workflows

### DeepSeek Harness Native Capabilities

Prefer the current Harness's built-in execution and orchestration mechanisms.

Use:

- Ordinary Agent execution for straightforward tasks.
- Existing Skills for specialist methods.
- Subagents for a small number of independent tasks.
- Harness Workflow orchestration for complex, coordinated, or parallel tasks.
- Existing project scripts for repeatable build and test operations.

Verify current Harness Workflow APIs and persistence behavior before implementing reusable orchestration.

### Existing Reusable Workflows

Search for established workflows when a task is recurring or has multiple stable steps.

Evaluate whether the workflow:

- Matches the current task.
- Is compatible with DeepSeek Harness.
- Has understandable inputs and outputs.
- Handles errors and partial failure.
- Avoids unnecessary Agent or tool overhead.
- Can be verified.

## Resource Adoption Policy

The project follows a minimal-adoption approach.

Before introducing a new Skill, MCP server, Plugin, Workflow, framework, or documentation file, identify:

1. The actual problem.
2. The proposed solution.
3. Why existing capabilities are insufficient.
4. The maintenance and complexity cost.
5. The cost of not introducing it.

Prefer the smallest adequate solution.

A resource should be adopted only when it solves a demonstrated need and can be maintained responsibly.

Update this file when a resource becomes adopted, is replaced, is found unsuitable, or becomes a significant project reference.

Do not record every search result or temporary research observation here.

Keep this index curated, useful, and aligned with the current project phase.
