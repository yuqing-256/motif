# Motif Implementation

## 1. Purpose

This document defines the technical starting point and how Motif adopts the selected tools. It intentionally keeps the initial project simple. Motif-specific abstractions are introduced only when the relevant roadmap stage requires them.

The A0 objective is a clean, reproducible, working technical baseline—not a fully Motif-styled website or a deeply customized Fumadocs implementation.

## 2. Approved initial stack

| Concern          | Initial choice     | Responsibility                                               |
| ---------------- | ------------------ | ------------------------------------------------------------ |
| Application      | Next.js App Router | Routing, rendering, application build                        |
| Language         | TypeScript         | Types and application code                                   |
| Package manager  | pnpm               | Dependency installation and lockfile                         |
| Styling          | Tailwind CSS       | Utility styling and CSS compilation                          |
| Component source | shadcn/ui          | Editable component source and configuration                  |
| Initial style    | Sera preset        | Temporary starting visual and component expression           |
| Primitive base   | Base UI            | Underlying interaction primitives                            |
| Documentation    | Fumadocs + MDX     | Documentation source, navigation, TOC, search infrastructure |

Exact versions come from the actual initial install and lockfile. Verify compatibility against current official documentation during setup and record the installed versions.

## 3. Initial project setup (A0)

Use the official initialization tools in this order.

### 3.1 Next.js

```bash
pnpm create next-app@latest motif
cd motif
```

Choose the recommended App Router setup with TypeScript, ESLint, Tailwind CSS, and the `@/*` import alias. Use pnpm and follow current CLI prompts and generated defaults. Treat the generated project tree as authoritative for the installed CLI version.

### 3.2 shadcn Sera + Base UI

Run the shadcn CLI from the existing Next.js project root:

```bash
pnpm dlx shadcn@latest init
```

Follow the interactive prompts and select **Sera** as the visual preset and **Base UI** as the component base when prompted. Complete initialization, then verify the generated `components.json`, package dependencies, CSS variables, utility files, and paths.

During the interactive initialization, select **Sera** as the visual preset and **Base UI** as the component base. Keep the generated theme variables intact through A0 so the starter remains reproducible. Motif theme adaptation begins in A2, guided by the approved visual specifications.

### 3.3 Fumadocs

From the same project root:

```bash
pnpm dlx @fumadocs/cli@latest init
```

Review the CLI diff before accepting it. The CLI configures Fumadocs in the existing Next.js application and may create a dedicated route group with its provider/layout and search route. It can also modify framework configuration, global CSS, the root layout, and `.gitignore`. Exact generated paths depend on the project and CLI version; inspect the actual output instead of assuming a fixed tree.

Fumadocs Blog integration, full documentation content, and blog functionality belong to A5. A0 establishes the shared documentation infrastructure.

### 3.4 Complete required MDX type setup

After the Fumadocs CLI finishes, inspect the installed dependencies. The CLI does not necessarily install every type package referenced by the documented MDX component examples. If `@types/mdx` is absent, add it explicitly:

```bash
pnpm add -D @types/mdx
```

Keep the documented type import when required by the installed Fumadocs setup:

```tsx
import type { MDXComponents } from "mdx/types";
```

Resolve missing type dependencies explicitly and keep TypeScript declarations aligned with the installed packages.

### 3.5 Global CSS and Fumadocs theme integration

Import the application's global stylesheet once from the root App Router layout, normally `app/layout.tsx`:

```tsx
import "./globals.css";
```

A route group such as `(docs)` does not create a CSS scope. Import the application-wide `global.css` once from the root layout; documentation layouts inherit that stylesheet.

Retain the Fumadocs CSS imports/configuration generated by the CLI. Inspect the resulting stylesheet before adding imports, and keep each required import in one place. When using the Shadcn integration, the relevant Fumadocs stylesheet setup commonly includes:

```css
@import "tailwindcss";
@import "fumadocs-ui/css/shadcn.css";
@import "fumadocs-ui/css/preset.css";
```

Preserve the generated shadcn theme variables in the stylesheet referenced by the project's actual `components.json` configuration. Keep one authoritative theme-variable location and adapt the generated setup only when a verified integration need requires it.

Important distinction: the Fumadocs Shadcn adapter maps Fumadocs theme colors to Shadcn CSS variables. It does **not** convert every Fumadocs component to the Sera visual style. Fumadocs retains its own layout and component presentation. The CLI may reuse compatible Shadcn `button`, `popover`, and `collapsible` components, but this is not a wholesale replacement of Fumadocs UI.

A0 verifies the shared stylesheet, theme variables, and supported component reuse. Fumadocs navigation, table of contents, search UI, and MDX presentation are reviewed and adapted during the later publishing stages.

### 3.6 Verify the baseline

Use scripts that actually exist in the generated `package.json`. Run the production build and inspect the application with the development server in a separate terminal:

```bash
pnpm build
pnpm dev
```

Verify:

- The root Next.js application loads.
- The generated Fumadocs route loads.
- An MDX page compiles and renders.
- The Fumadocs search endpoint/UI works in the generated setup.
- Global CSS is loaded once from the root layout.
- Fumadocs theme colors resolve through the Shadcn CSS variables.
- Any reused Shadcn primitives work with the Fumadocs components that consume them.
- Light/dark theme behavior works if enabled by the generated setup.
- Desktop and mobile default documentation layouts remain usable.

Review all generated/modified files and the lockfile. Record the commands and results in the A0 implementation report.

### 3.7 Non-blocking Next.js navigation diagnostics

The current Next.js version may emit an `instant-shell-url-data` diagnostic for a generated Fumadocs page that awaits route `params` outside a Suspense boundary. If the route still builds, renders, and functions correctly, treat this as a non-blocking navigation/performance diagnostic during A0.

- Record the affected route and diagnostic for later navigation-performance review.
- Apply `export const instant = false` when the installed versions and a reproducible test demonstrate that it is the appropriate fix.
- Revisit the diagnostic when the installed Next.js/Fumadocs versions provide a verified recommended integration pattern.

Actual compilation failures, runtime errors, broken routes, or failed MDX rendering are not deferred; those must be resolved before the baseline is considered usable.

## 4. Tool responsibilities and design authority

- **Motif owns:** identity, governing visual language, tokens, typography, photography direction, geometry, grid, color, component meaning/variants, page composition, content semantics, provenance, and user experience.
- **Sera provides:** the initial shadcn visual/component baseline. It is neither immutable nor the final Motif theme.
- **shadcn provides:** editable primitive source, component configuration, and registry installation. It does not own Motif's visual direction.
- **Base UI provides:** the selected primitive interaction foundation. Preserve its semantics and accessibility behavior unless an approved technical reason requires adaptation.
- **Fumadocs provides:** MDX processing, content sources, page tree, table of contents, documentation navigation, and search infrastructure. It does not own Motif page appearance or information architecture.
- **Tailwind provides:** utility and compilation capabilities; it is not a competing token authority.
- **Next.js/React provide:** routing, rendering, and interaction mechanisms; Motif defines editorial logic.

## 5. Progressive implementation boundaries

### A0 — generated technical baseline

Keep the generated structure close to the official initializer output. Verify the framework, shadcn configuration, Sera selection, Base UI dependency, Fumadocs routes, MDX, global stylesheet, and theme adapter. Record actual versions and generated paths.

### A1 — baseline freeze

Inspect the complete repository and lockfile. Reconcile `README.md`, `PACKAGE-MANIFEST.json`, implementation notes, `.gitignore`, and `.gitattributes` with the actual generated project. Establish the Git workflow and commit the complete starter with the authoritative Alpha documentation.

### A2 — visual foundation

Inspect Sera's CSS variables, typography, geometry, spacing, and component presentation in a browser. Build a small internal specimen surface and establish Motif's approved tokens. Map shadcn, Fumadocs, and Tailwind variables to one Motif source of truth.

### A3 — shadcn adaptation

Keep shadcn-derived primitive source editable in the generated component location. Select components from actual interface requirements and adapt them to approved Motif tokens. Preserve Base UI semantics and keyboard behavior. Add Motif semantic components when stable meaning, content structure, provenance, accessibility contracts, and reuse justify them.

### A4 — component validation

Build internal component specimens and test examples. Define finite approved variants and adaptive behavior for viewport, container, content length, writing system, direction, and input conditions. Add unit, integration, browser, accessibility, and visual-regression checks as the implementation becomes testable. Keep previews separate from production routes.

### A5 — publishing surfaces and Fumadocs customization

```text
One Next.js App Router application
├── /                 Motif website
├── /docs/*           Fumadocs documentation
└── /blog/*           Fumadocs MDX / Blog content
```

Use separate layouts and content collections where useful. Customize Fumadocs layout components when Motif's design and information architecture are established. Prefer official customization mechanisms and local components; evaluate upstream forks only when public extension points cannot support the required behavior. Verify route conventions against the installed Fumadocs version.

## 6. Component and token contracts

When a token system is approved, maintain one Motif semantic source of truth:

1. Primitive values: approved raw color, type, spacing, and geometry values.
2. Semantic tokens: roles such as canvas, surface, ink, text-muted, signal, border, focus, and type/layout roles.
3. Composition values: local exceptions justified by an approved Composition Brief.

Light/Dark use the same semantic names and component APIs. Upstream library variables are mappings. Components use semantic tokens and the approved scales; local exceptions require a Composition Brief.

A primitive handles interaction; a semantic component expresses meaning; a composition pattern organizes content; a page determines the complete composition. See `docs/ARCHITECTURE.md` and `docs/content/CONTENT-MODEL.md`.

## 7. Layout, responsive behavior, and localization

Use CSS Grid/Flexbox, intrinsic sizing, `minmax()`, `min()`, `max()`, `clamp()`, and container queries to implement approved relationships. Separate viewport conditions from component-container conditions, use logical CSS properties for writing direction, and keep the three publishing surfaces independently composed within their shared visual foundation.

Verify actual glyph coverage, font licensing, loading/fallback, CJK punctuation and line breaking, long labels, RTL direction, and content expansion for languages the product claims to support.

## 8. Fonts, photography, and graphics

- Use approved font files; verify source, license, weights, glyph coverage, fallback, loading behavior, and layout shift.
- Use responsive image sources and meaningful crop decisions; preserve source, rights, caption, credit, and description.
- Prefer CSS/basic primitives for simple geometry. Use SVG for meaningful diagrams, maps, charts, complex data graphics, or approved identity marks.
- Keep chart data and transformations separate from presentation; provide text/structured-data alternatives.

## 9. Dependencies and verification

Use only dependencies authorized by the current roadmap stage. A0's approved initialization tools and the explicitly required MDX type dependency are the sole exception to the general requirement for owner approval before adding dependencies. Later changes require a rationale covering need, compatibility, alternatives, license, maintenance, and lockfile impact.

Use scripts present in the repository and confirm the available test runner from the package manifest. Verification grows by stage as defined in `docs/system/QUALITY.md` and `docs/testing/TEST-SUITE.md`.
